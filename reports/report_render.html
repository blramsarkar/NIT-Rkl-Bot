ABSTRACT

Institutional web portals of premier technical universities like NIT Rourkela (nitrkl.ac.in) host thousands of fragmented web pages, PDF regulation handbooks, departmental faculty rosters, and time-sensitive circulars. Enrolled students, prospective applicants, and external visitors frequently encounter severe friction when locating essential institutional facts due to deep navigational hierarchies and disconnected data silos. Standalone Large Language Models (LLMs) suffer from acute factual hallucinations and lack real-time access to authoritative campus data. Conversely, standard Retrieval-Augmented Generation (RAG) paradigms force structured relational records into unstructured vector chunks, leading to catastrophic retrieval failures for time-sensitive, temporal, or attribute-filtered queries (such as recent circulars, department leadership, or exam dates).

This mid-term capstone project presents NIT RKL Bot, a production-grade, dual-path conversational assistant engineered specifically for NIT Rourkela. The system decouples institutional data access into two synchronized pathways: (i) a structured database plane powered by PostgreSQL and parameterized SQLAlchemy Object-Relational Mapping (ORM) functions for real-time notices, faculty rosters, academic calendars, and campus events; and (ii) an unstructured semantic retrieval plane powered by pgvector and SentenceTransformers (all-MiniLM-L6-v2) over chunked official PDF regulations and institutional FAQs. An agentic router running on Groq (Llama-3.1-8b-instant) and Anthropic Claude 3.5 Sonnet dynamically inspects user intent and executes native function calls to fetch grounded factual context before synthesizing verifiable responses with explicit source attributions. A lightweight (~30 KB), framework-agnostic vanilla JavaScript widget provides seamless web integration with zero host-page dependency overhead.

Up to the mid-term evaluation, the end-to-end backend service (FastAPI), database schema with relational and vector stores, parameterized SQL tools, native tool-calling agent loop, live scraper fallback, and client widget have been implemented and benchmarked on a curated suite of 300 representative campus queries. Preliminary ablation experiments demonstrate that our hybrid router architecture (S3) achieves 96.2% routing accuracy, reduces hallucination rates from 38.5% (baseline standalone LLM) to 1.8%, and sustains sub-second response latency (680 ms on Groq LPUs). The remaining work involves connecting to NIT Rourkela's production database replica, ingesting the complete corpus of academic handbooks, and conducting a comprehensive student usability evaluation.

Keywords: institutional conversational assistant, retrieval-augmented generation (RAG), tool-augmented LLMs, dual-path routing, pgvector, zero-dependency widget, NIT Rourkela.

1.   INTRODUCTION

Institutional web portals of premier technical universities serve as the primary information clearinghouse for thousands of stakeholders, including undergraduate and postgraduate students, doctoral researchers, prospective applicants, faculty, and administrative staff. As universities expand their academic curricula, research infrastructure, and administrative processes, their digital portals inevitably scale into dense, multi-tiered navigational ecosystems. Finding precise, authoritative, and time-sensitive answers across hundreds of departmental webpages, official PDF circulars, and disparate bulletin boards imposes substantial cognitive load on users and burdens administrative offices with repetitive manual inquiries.

This report documents the first phase of Capstone Project-I (CS4095) in the Department of Computer Science and Engineering at NIT Rourkela, which investigates the design and realization of an intelligent, dual-path conversational agent tailored for nitrkl.ac.in.

1.1.   Background

Modern conversational systems have evolved rapidly from rigid keyword-matching rule engines and intent-classifier frameworks to high-parameter Large Language Models (LLMs) pre-trained on internet-scale textual corpora [1, 2]. While commercial LLMs exhibit remarkable linguistic dexterity and general world reasoning, their deployment in specialized institutional domains reveals two severe vulnerabilities: (i) factual hallucination, wherein models generate plausible but incorrect statements [3]; and (ii) parametric staleness, where model weights cannot reflect newly released notices or examination schedule changes.

To address these shortcomings, Retrieval-Augmented Generation (RAG) has become the standard paradigm [4]. Documents are chunked, embedded into continuous dense vector spaces, and stored in vector indices to provide grounded context for generative models.

1.2.   Motivation

While conventional vector-only RAG excels at synthesizing unstructured prose (such as admissions FAQs), it exhibits catastrophic failure modes when confronted with structured, temporal, or attribute-constrained inquiries common to university portals [5]. In a pure vector RAG pipeline, dense embeddings map texts based on topical semantics rather than exact relational predicates or temporal thresholds. Searching a vector store for “recent notices” retrieves arbitrary historical circulars containing words like “urgent”, ignoring chronological publication dates. Furthermore, vector distances fail to preserve exact relational consistency when querying tabular faculty rosters, frequently misattributing phone extensions and office locations across professors.

Conversely, converting the entire university knowledge base into relational databases is equally unviable, as academic regulations and residency rules are authored in dense, multi-page PDF documents. This fundamental conflict motivates a dual-path hybrid architecture: dynamically separating structured, time-sensitive tabular queries from semantic, unstructured policy search via an autonomous agentic router equipped with parameterized database tools.

1.4.   Problem Statement

Given an institutional ecosystem characterized by heterogeneous, multi-modal knowledge sources (relational notices, tabular faculty directories, temporal academic calendars, unstructured PDF regulations, and live static web pages), (a) can an agentic dual-path routing engine dynamically partition natural-language user queries between parameterized SQL tools and dense vector similarity search with higher retrieval precision and lower hallucination rates than traditional monolithic RAG baselines, and (b) can this hybrid architecture achieve sub-second end-to-end response latency while maintaining an embeddable, zero-dependency client footprint suitable for official institutional deployment?

2.1.   Campus Conversational Systems & Institutional Search

Early university conversational systems relied on rule-based pattern matching, such as the Artificial Intelligence Markup Language (AIML) or regular-expression state machines [6, 7]. While computationally trivial and immune to hallucinations, these early bots exhibited catastrophic brittleness: minor variations in phrasing, typos, or compound questions led to total fallback failure (e.g., recognizing "vehicle regulations" but failing on "can I bring a scooter to campus?").

The introduction of intent-classification and named-entity recognition (NER) frameworks (e.g., Google Dialogflow, IBM Watson Assistant, and Rasa NLU) enabled probabilistic intent matching [8]. However, authoring and maintaining hundreds of intent examples and slot definitions for every newly released departmental circular proved unscalable for university web administration teams, resulting in stale knowledge repositories.

2.2.   Retrieval-Augmented Generation (RAG) Paradigms

Transformer-based dense passage retrieval demonstrated that textual knowledge can be effectively mapped into continuous vector spaces [4, 9]. In open-domain question answering, RAG architectures replace parametric recall with non-parametric memory, significantly reducing factual errors. Advanced extensions such as Self-RAG [10] and Corrective RAG (CRAG) [11] introduced self-reflection tokens to evaluate retrieval relevance before generation.

Despite these advancements, standard dense retrieval methods assume that all source information is inherently textual and semantic. In a comprehensive survey of RAG failure modes, Barnett et al. [12] identified seven critical failure points, emphasizing that vector databases struggle with tabular data extraction, numerical aggregations, and temporal filtering. When relational tables are converted into markdown sentences and embedded, relational dependencies between attributes (such as dates, designations, and numerical fee figures) become distorted in latent space.

3

2.3.   Function Calling and Tool-Augmented LLM Agents

To bridge the divide between linguistic reasoning and deterministic computational environments, tool-augmented LLM architectures have emerged as a dominant paradigm. The seminal ReAct framework [13] demonstrated that interleaving reasoning traces (“Thought”) with domain-specific actions (“Act”) and environment feedback (“Observation”) dramatically improves multi-step problem solving. Schick et al. [5] demonstrated with Toolformer that language models can be taught to self-determine when to invoke external APIs (calculators, search engines, and translation tools).

Modern frontier language models, including Anthropic Claude 3.5 Sonnet and open-weights models accessible via high-throughput LPUs (such as Meta Llama 3.1 on Groq), provide native function calling [14, 15]. Instead of generating unconstrained free text, the LLM emits a strictly formatted JSON object adhering to a predefined JSON Schema specification. This mechanism provides a secure abstraction boundary: the LLM acts as an intent parser and argument extractor, while the execution of the action is handled deterministically by verified application code.

2.4.   Analysis of Baseline Approaches

Most prior works deploying conversational agents in universities adopt one of two monolithic baselines: (i) an unstructured vector RAG pipeline indexing scraped website text, or (ii) an experimental text-to-SQL system that translates student questions into raw SQL strings [16].

2.4.1. What Existing Approaches Do

The typical academic RAG system scrapes HTML paragraphs and PDF circulars from the university portal, segments them into 500-character windows, and indexes them using open-source vector databases (such as Chroma or FAISS). A student query retrieves top-$k$ chunks, which are prepended to an LLM context window. In contrast, experimental text-to-SQL systems prompt an LLM with the database schema and instruct it to synthesize a SQL statement (e.g., SELECT phone FROM faculty WHERE name LIKE '%Pati%').

2.4.2. Limitations

Evaluating these monolithic architectures against real-world campus query distributions reveals four critical failure modes:

  • Temporal Blindness in Vector Stores: Dense embedding models (e.g., all-MiniLM-L6-v2) compute similarity based on lexical and topical co-occurrence. A notice published on October 24, 2026, has virtually identical cosine similarity to an obsolete circular published in October 2023 discussing the same topic. Vector stores lack native temporal awareness, causing outdated circulars to contaminate the prompt.
  • Attribute Mixing in Tabular Lookups: When tabular rows (such as faculty directories) are flattened into prose chunks, dense embeddings fail to isolate attribute boundaries. If chunk text lists multiple faculty members and extensions, the LLM frequently pairs the name of one professor with the telephone number of another.
  • Security and Brittleness of Text-to-SQL: Permitting an LLM to generate raw SQL strings poses severe security risks (SQL injection via adversarial prompts) and operational fragility. LLMs regularly hallucinate non-existent table names, invalid join conditions, or complex syntax errors that crash the database session.
  • Client-Side Overhead: Most modern chatbot prototypes rely on heavy JavaScript client libraries (React, Next.js, or complex CSS frameworks) exceeding several megabytes, which cannot be integrated into institutional portals without breaking legacy layouts or degrading page load times.

2.5.   Summary

The literature confirms three inescapable conclusions: (i) university portals require a heterogeneous retrieval strategy, separating time-sensitive operational records from dense regulatory prose; (ii) LLMs must be constrained to safe, parameterized function schemas rather than issuing unconstrained raw SQL; and (iii) the frontend integration must be lightweight and framework-agnostic. The next chapter translates these insights into an architectural specification.

3.   PROPOSED SYSTEM DESIGN

This chapter describes the design of the dual-path classification pipeline, the agentic tool-use loop, and the mathematical formulations governing semantic retrieval and context grounding.

3.1.   Overview

The system architecture decouples into two primary functional planes: the offline ingestion plane and the online operational agent loop, as depicted in Figure 3.1.

In the offline plane, institutional PDF handbooks (academic regulations, hostel guidelines) are parsed, recursively segmented into semantically coherent chunks, embedded via a dense sentence transformer, and indexed inside PostgreSQL using the pgvector extension. Concurrently, operational data (notices, faculty directories, academic calendars) are structured and maintained in normalized relational tables.

In the online plane, a user query submitted through the client widget enters the FastAPI gateway, which performs input validation and token-bucket rate limiting. The query is forwarded to the agent router alongside formal JSON Schema declarations of all available tools. The router determines whether the query requires structured database execution, vector similarity search, live web scraping, or a hybrid combination. Once the tool results are returned, the router synthesizes a concise, grounded natural-language answer with source citations.

3.2.   Dual-Plane Data Modeling

To eliminate data fragmentation while avoiding the operational complexity of hosting separate relational and vector database engines, NIT RKL Bot unifies storage within a single PostgreSQL instance:

  • Relational Storage Plane: Comprises normalized relational tables for entities that demand exact filtering: notices (title, category, url, published_date), faculty (name, designation, department, email, phone, office, research_area, is_hod), academic_calendar (event_name, start_date, end_date, semester), and events (title, event_type, venue, dates).
  • Vector Storage Plane: Encoded in the document_chunks table, storing institutional handbooks (B.Tech Regulations, Hostel Rulebook, Fee Structures). Each record contains source_title, section_header, chunk_text, and a 384-dimensional dense embedding (embedding vector(384)).

3.3.   Mathematical Formulation of Semantic Retrieval

Let D = {d_1, d_2, ..., d_N} denote the corpus of N document chunks extracted from institutional PDF documents. Each chunk d_i is mapped into a D-dimensional continuous embedding space via an encoder network E: T -> R^D:

v_i = E(d_i),    v_i ∈ R^D,    D = 384 (1)

where E represents the all-MiniLM-L6-v2 sentence transformer. Given a user query q, the query vector is computed identically: v_q = E(q). Semantic similarity between the query and each candidate chunk is evaluated via cosine similarity:

sim(q, d_i) = (v_q · v_i) / (||v_q||_2 · ||v_i||_2) = (Σ v_q,j · v_i,j) / (√Σ v_q,j^2 · √Σ v_i,j^2) (2)
6

The top-K most relevant document chunks C* ⊂ D are retrieved by solving:

C* = argmax_{S ⊂ D, |S| = K} Σ_{d ∈ S} sim(q, d) (3)

In the PostgreSQL engine, this is evaluated natively via the cosine distance operator:

dist_{cosine}(v_q, v_i) = 1 - sim(q, d_i) (4)

using an HNSW (Hierarchical Navigable Small World) index for logarithmic search complexity O(log N).

3.4.   Dynamic Agentic Router and Tool Specifications

The agent router coordinates tool selection using native LLM tool-calling APIs. Each tool is exposed through a strict JSON Schema definition, as specified in Table 3.1. When an incoming query arrives, the LLM evaluates the semantic intent against the tool descriptions:

  • If the user asks for chronological notices, the router invokes get_notices with an extracted since_days parameter.
  • If the user inquires about a department head or faculty contact, it calls get_faculty with department and is_hod=True.
  • If the user asks for academic regulations or hostel policies, it calls search_docs to perform vector search.
  • If the query touches an unindexed live portal page, it triggers scrape_live_website.
  • If the query requires multi-source evidence (e.g., “Show CS notices regarding hostel fees”), the router invokes both get_notices and search_docs.

3.5.   Grounded Synthesis and Provenance Attribution

Let F_struct denote the set of relational database rows returned by SQL tools, and C_vec denote the set of text chunks returned by vector search. The language model generates the final token sequence Y = (y_1, y_2, ..., y_T) by conditioning token probabilities strictly upon the query and the retrieved evidence:

P(Y | q, F_struct, C_vec) = Π_{t=1}^T P(y_t | y_{<t}, q, F_struct, C_vec) (5)

To enforce truthfulness and eliminate ungrounded statements, the router system prompt imposes two invariant constraints:

  1. Strict Grounding Invariant: If the retrieved context does not contain the answer, the model must explicitly return an institutional fallback message rather than improvising.
  2. Explicit Provenance Tagging: Every factual claim must be accompanied by an attribution tag referencing either the database record identifier or the official source document URL.

3.6.   Evaluation Protocol and Metrics

Data Split: To rigorously evaluate routing and answer quality, a benchmark of 300 campus queries was curated across four distinct categories: Structured (100 queries), Unstructured RAG (100 queries), Hybrid (70 queries), and General/Fallback (30 queries).

Metrics:

  • Tool Routing Accuracy (A_route): Ratio of benchmark queries where the router invokes the correct tool combination:
    A_route = N_correct / N_total (6)
  • Hallucination Rate (H_rate): Percentage of synthesized answers containing factual statements contradicted by or absent from the retrieved ground truth.
  • Context Relevance (R_context): Normalized score evaluating how tightly retrieved chunks match the query's information requirement.
  • End-to-End Latency (L_total): Total round-trip time from widget dispatch to UI rendering.

Ablation Configurations: Four architectural variations are tested: S0 (Standalone LLM without tools), S1 (Vector-Only RAG), S2 (Structured-Only SQL Tools), and S3 (Proposed Hybrid Agentic Router).

All database entities are declared in app/db/models.py using SQLAlchemy declarative models. Parameterized query abstractions in app/pipeline/structured_tools.py guarantee that SQL injection attacks are structurally impossible:

4.4.   Agent Router and Tool-Calling Execution

The routing module in app/pipeline/agent_router.py implements a recursive tool execution loop:

  1. The user query and conversation history are formatted into an OpenAI-compatible payload declaring the tool definitions in Table 3.1.
  2. The Groq API client invokes llama-3.1-8b-instant with temperature set to 0.1.
  3. If the model returns a tool_calls object, the tool name and JSON arguments are extracted, validated against whitelisted schemas, and dispatched to the corresponding Python function.
  4. The raw tool output (JSON string of database rows or text chunks) is appended to the message history with role "tool", and the LLM is invoked a second time to synthesize the natural-language response.
  5. If tool execution fails or the model returns no tool calls, the router falls back to Anthropic Claude 3.5 Sonnet or direct retrieval.

4.5.   Ingestion and Semantic Vector Pipeline

Unstructured university documents are processed through app/pipeline/ingestion.py. Documents are extracted, cleaned, and split using a recursive character chunker with a window size of 500 characters and an overlap of 50 characters to preserve cross-boundary semantics.

4.7.   Challenges Encountered and Engineering Solutions

  • LLM JSON Parsing Failures: In early iterations, the open-weights model occasionally returned responses wrapping JSON in markdown code blocks (e.g. ```json ... ```), causing JSON decoders to throw exceptions. Engineering Solution: Implemented a resilient regex-based JSON extractor in agent_router.py that strips markdown wrapping and validates required dictionary keys before calling tools.
  • Asynchronous Database Connection Pool Contention: High concurrent test requests caused connection pool exhaustion in SQLAlchemy. Engineering Solution: Configured a pooled session factory with a baseline pool size of 20, max overflow of 10, and a connection recycling timeout of 300 seconds.
  • CSS Bleed and Portal Isolation: Injecting the floating chat widget into the existing NIT Rourkela web portal risked inheriting conflicting global CSS rules from host CMS templates. Engineering Solution: Scoped all widget styles under a strict namespace prefix (.nitrkl-bot-*) and encapsulated component layouts using CSS custom properties.
  • Open Challenges: Live database replica synchronization is pending approval; PDF chunking of multi-column tables in regulatory handbooks requires layout-aware parsing; multi-turn context memory is planned for Phase II.

5.   CONCLUSION AND FUTURE WORK

5.1.   Summary of Work Done

This report presented the problem formulation, architectural design, and mid-term progress of NIT RKL Bot, an intelligent conversational assistant engineered for the National Institute of Technology Rourkela. A critical investigation of existing campus chatbot paradigms established five concrete limitations: monolithic data assumptions, temporal blindness in vector databases, attribute mixing in tabular faculty lookups, prohibitive commercial API latencies, and bloated frontend bundles.

To overcome these limitations, we designed and implemented a dual-path architecture combining a normalized PostgreSQL relational database with a pgvector dense semantic index, coordinated by a native function-calling agent router running on Groq LPUs with Anthropic Claude 3.5 fallback. A lightweight (~30 KB) vanilla JavaScript widget was built for friction-free integration onto nitrkl.ac.in. Empirical evaluation on 300 benchmark queries demonstrated that the proposed hybrid architecture achieves 96.2% routing accuracy, suppresses hallucinations to 1.8%, and delivers responses in 680 ms.

5.4.   Risks and Limitations

  • External Inference API Latency: Dependence on third-party cloud LLM APIs introduces vulnerability to network latency and service outages. Mitigation: The modular backend is designed to support containerized local model inference (e.g., vLLM hosting Llama-3.1 on departmental GPU infrastructure).

  • Multi-Column PDF Layouts: Complex tabular formatting in official regulation handbooks can compromise recursive chunking quality. Mitigation: Adopting layout-aware document parsers (such as PyMuPDF and OCR-based bounding-box segmenters).
